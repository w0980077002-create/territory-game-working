## Решения с наибольшим эффектом

1. Сохранить красные алмазы Верфи и их игровую покупательную способность. Для возможных реальных призов ввести отдельный баланс с полным покрытием USDT и выделенным резервом TON. Призовые режимы должны иметь одинаковые для всех участников правила и экипировку.
2. Начать с пяти игровых кораблей и общего лимита добычи. Проверить торговые и разведывательные специализации и ремонт до выпуска платного корабля. Цена 250 XTR соответствует $5 только при цене приобретения $0,02/XTR. При опубликованной выплате $0,013/XTR проект получает номинальный эквивалент $3,25 до остальных удержаний.
3. Сбалансированный разбор даёт финальному платному кораблю до 480 привязанных синих алмазов с учётом уже полученных экспедиционных алмазов, плюс 30% фактически вложенных ресурсов. За 250 XTR витрина даёт 550 самоцветов, при первом заказе 1 100. Ценность корабля строится на игровых маршрутах, материалах, продаже и экипировке. Сравнение требует учёта различий в ассортименте каждого кошелька.
4. Перед новой эмиссией измерить реальное поведение. Последние результаты Claude показывают крупные расходы у активно инвестирующего героя. Темп накопления резко меняется с политикой трат. Слабые поздние трофеи подтверждены прошлым прогоном, а общая инфляция ещё требует данных об обороте и покупках.
5. Тестовые Stars и подключение кошелька уже существуют. Перед массовыми продажами проверить первую покупку при нескольких подтверждениях, возвраты после перевода покупок в Solo, сверку выплат и права администратора. Для денежных призов первое согласование включает допустимость механики для украинского ФОП и выбранных стран, второе включает конкретный обеспеченный бюджет.
6. В календарной матрице завершены 21 прогон по семи сценариям. Ограниченное время боя после первого дня не позволяет подтвердить темп полной ежедневной игры. [Сводка игроков](players.md)
7. В среднем сценарии со 100 000 регистраций получаются 25 000 MAU, 6 000 DAU и 625 плательщиков. Модель даёт $5 281 очищенного месячного дохода, $1 018 целевого фонда и примерно $2 025 после допущенных затрат и резервов. При 10 000 регистраций поток отрицателен на $274 в месяц и новый фонд равен нулю. Это проверка чувствительности к масштабу, условиям оплаты и расходам. [Таблица модели](tables/finance.csv)

## Воспроизводимость

Запускать из корня репозитория с Node 24, зависимостями из lockfile и Python 3.

```sh
node --import tsx scripts/sim/economy/catalog.ts
node --import tsx scripts/sim/economy/cave.ts > docs/economy-1.0/tables/cave_repeats.json
python scripts/sim/economy/valuation.py
python scripts/sim/economy/model.py
python scripts/sim/economy/ledger_check.py
bash scripts/sim/economy/run-year.sh
# Календарная матрица из отчёта
SIM_LATE_SECONDS_PER_MINUTE=.05 SIM_OUTPUT=.tmp/economy-calendar bash scripts/sim/economy/run-year.sh
python scripts/sim/economy/summarize.py .tmp/economy-calendar calendar
# Более продолжительный тест с ограничением времени боя с дня 2
SIM_LATE_SECONDS_PER_MINUTE=1 SIM_OUTPUT=.tmp/economy-bounded \
  SIM_PROFILES='30:0:17 30:0:29 30:0:47 90:0:17 90:0:29 90:0:47 180:0:17 180:0:29' \
  bash scripts/sim/economy/run-year.sh
python scripts/sim/economy/summarize.py .tmp/economy-bounded bounded
# Контрольная неделя без сокращения боёв
SIM_DAYS=7 SIM_PROFILES='90:0:17 90:0:29' SIM_OUTPUT=.tmp/economy-first-week bash scripts/sim/economy/run-year.sh
python scripts/sim/economy/summarize.py .tmp/economy-first-week first_week 7
```

`SIM_JOBS` задаёт число параллельных профилей. Команда `SIM_DAYS=14 node --import tsx scripts/sim/economy/year.ts 90 0 17 berserker` запускает один профиль. Установленный лимит используется для воспроизводимого быстрого сравнения. Полный прогон при фиксированном тике 50 мс может занять часы для всей матрицы. На итог влияют длительность боя, число побед и состояние сохранения. [Описание ограничений](players.md)

## Проверки

На исходном игровом SHA прошли сборка и 428 автоматических тестов, включая локальные сетевые проверки Арены. Повтор первого дня с seed 17 дал тот же снимок, независимые выгрузки каталога совпали по SHA-256. Отдельно проверены повторный сбор в Пещере, сверка денежных остатков в профилях, целочисленный резерв, уникальность выплаты и закрытие заявки. Проверка модели реестра выполнялась в памяти без сети. Физические проверки платежей и кошелька в этой исследовательской ветке не проводились. Статус текущего платежного среза приведён по #81.
