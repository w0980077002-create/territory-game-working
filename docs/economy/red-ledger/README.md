# Этап 5 · обеспеченные красные алмазы

Пакет для согласования включает офлайн-модель, закрытую миграцию PostgreSQL и отдельную Edge Function `vvr-red-ledger`. Модель работает с тестовыми проводками. Серверная часть не развёрнута, кошелёк, ключи и блокчейн-провайдер не подключены. Игровые красные из Верфи остаются в прежних сохранениях и вне финансового реестра.

## Реестр

- 1 обеспеченный алмаз = 1 USDT. В хранилище целые единицы по 0,0001. Списание 0,03 равно 300 единицам. Минимум вывода в модели 5 USDT, рабочий диапазон для согласования 3–5.
- Операционные счета разделены на подтверждённое покрытие, нераспределённый фонд, доступный и заблокированный пользовательские остатки и сетевые комиссии. Покрытие равно сумме фонда и обязательств. Выдача из фонда, списание и удержание выполняются целиком одной транзакцией. Сумма комиссии списывается из отдельного резерва.
- Пополнение признаётся после независимой сверки актива, сети, адреса казны, суммы и финального подтверждения. Транзакция пополнения и событие награды имеют уникальные ключи. Доступ к записям дают аутентифицированные роли. Прошлые записи исправляются сторнирующими проводками. Административный API возвращает закрытые сводку и журнал. Любая будущая публичная статистика должна агрегировать суммы и количество выплат без адресов и персональных данных.
- Награды разрешаются лишь за утверждённые бесплатные активности по проверенным событиям и в лимите фонда. Stars, реклама, рыночная комиссия, платные корабли, материалы, тестовые остатки и клиентские сохранения не создают финансовых обязательств. Каналы награждения требуют отдельного допуска и проверки косвенных преимуществ, ботов и сговора.

## Ручной вывод

1. Аутентифицированный игрок указывает проверенный адрес для утверждённой сети. Сервер записывает заявку, снимок адреса и полностью удерживает сумму.
2. Оператор проверяет игрока, географию, источник награды, адрес и события риска. До 14 дней заявка получает решение. Отказ возвращает удержанное. Просрочка поднимает уведомление оператору, сумма остаётся зарезервированной до явного решения.
3. Одобрение резервирует максимум сетевой комиссии. Оператор сначала получает разовый допуск `dispatch` к ручной отправке. Повтор допуска возвращает статус `already_claimed`. Финализация в реестре только по подтверждённой транзакции, которая соответствует заявке по сети, активу, получателю, сумме, комиссии и идентификатору заявки. Уведомление должно содержать фактическое время цепочки после начала отправки. Идентификатор нельзя переиспользовать для новой заявки.
4. При неизвестном результате перевода оператор сверяет сеть. Заявку после начала отправки нельзя просто отменить и повторить внешнюю операцию. Админка разделяет проверки, ручное объявление результата и независимое подтверждение. Публичный мониторинг показывает суммарное покрытие и результаты выплат без адресов.

Допуск к пилоту требует выбора сети и токена, сверки наличия покрытия и резерва комиссий, юридического и финансового согласования, проверки полномочий и санкций, повторов заявок, параллельных действий операторов и теста сверки TXID. Тестовые награды из этой модели никогда не импортируются в реестр.

## Серверный контракт

- Edge принимает W066-сессию и передаёт в SQL только идентификатор из подписанной сессии. Игрок читает `state` и подаёт `request`. Суммы API передаются десятичными строками целых единиц, масштаб 10 000. Адрес проходит форматный контроль тарифицируемой сети и ручную сверку.
- Администратор с действующим разблокированным доступом владельца выполняет `admin_state`, `fund`, `fund_fee`, `award`, `approve`, `reject`, `dispatch`, `settle`. Каждое изменение требует UUID операции. Закрытая сводка показывает очередь и журнал. При выдаче оператор подтверждает допущенный бесплатный источник и событие. Фонд и бухгалтерские записи проверяют повторную выдачу и предел остатка.
- `/receipt` принимает только подписанное HMAC сообщение доверенного адаптера, который независимо читает финальную транзакцию и сопоставляет её с заявкой. Право оператора отправить команду не даёт права создавать доказательства. Нужны TXID, выбранная сеть и идентификатор токена, отправитель, получатель, сумма, нативная комиссия, время цепочки и UUID заявки для выплаты. Подтверждение принимает только точное совпадение и одно использование TXID. Секрет, сеть, токен, канонический формат адреса и резервы в черновике не заданы.
- В миграции закрыты три независимых допуска: реестр, новая выдача и новые заявки/отправка. Отправка выполняется вручную вне сервера. Автоперевода, обмена или начисления из Stars и игровых сохранений нет. Комиссии хранятся в целых единицах отдельного нативного актива.

## Проверка

`node --import tsx --test tests/red-ledger-prep.test.ts` проверяет офлайн-модель, а `tests/pg/w066-backed-red.sql` проверяет закрытый серверный реестр с тестовыми доказательствами в откатываемой транзакции.

Сценарии покрывают отказ при необеспеченной выдаче, дробную покупку, повторы подтверждений и блокировку суммы до проверки, выплату с отдельным сетевым резервом и разблокировку просроченной заявки при отказе.
