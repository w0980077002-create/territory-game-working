# Инструкции Claude Code — VIKING VS ROME

**Владелец принимает решения по изменениям.** Цель — точная реализация утверждённого пользовательского GDD, а не переизобретение игры. Содержимое этого файла фиксирует границы нового репозитория, не заменяет полное ТЗ.

## Жёсткие ограничения
1. Работай **только** в этом репозитории `w0980077002-create/territory-game-working`. Не изменяй `territory-game-builde`, `territory-next`, другие проекты или существующие продакшен-сервисы.
2. Не подключай боевой Supabase / текущего Telegram-бота, не используй prod env, ключи, реальную оплату или чужую базу данных. Для прототипа допускаются локальное состояние и полностью изолированное тестовое окружение.
3. Не переносить автоматически старую кодовую базу и ветки. От старой игры брать только явно утверждённые собственные визуальные ассеты и механики, поштучно и с проверкой происхождения.
4. Не заменяй обещанные игровые функции декоративными неработающими кнопками. Новые функции должны быть доступны игроку для реального теста.
5. Не изменяй название, набор систем, числовые значения, статусы и игровую экономику по собственной инициативе. Спорные вопросы и несоответствия GDD фиксируй отдельно.
6. Не копируй сторонний исходный код, фирменные игровые изображения, аудио, логотипы и персонажей из референсной игры; пиши свой код и создавай собственные ассеты.

## Приоритеты UX
- **Главный экран:** плотная мобильная композиция по присланному владельцем скриншоту: верхний HUD, длительный видимый живой бой, вертикальные боковые режимы, быстро доступная экипировка, крупное главное действие, нижние вкладки.
- **Движение и бой:** герой и 2 спутника слева, противники справа; читаемые атаки, попадания, действия; сцена не заменяется статичным постером. Реальная работа x1/x2, Auto, волн и босса.
- **Фон и стиль:** выразительное фактурное дерево из TERRITORY как собственный UI-стиль; живописная сцена с глубиной. Конкретные свои персонажи добавляются после отбора владельцем; комиксная эстетика и референсный экран — исходные требования GDD.
- **Телефоны:** в первую очередь вертикальные экраны 320, 360, 390, 430 px, safe areas и Telegram WebView, без случайного вертикального скролла боевой сцены и перекрытых кнопок.

## Технологический ориентир из GDD
TypeScript strict, Vite, React 19, Tailwind, Zustand, Phaser 3/Canvas, Telegram Mini Apps SDK; разделение боевой сцены и React UI. Технические детали должны быть подтверждены в ARCHITECTURE.md перед большим внедрением.

## Рабочий процесс
1. Принять и проанализировать **полный GDD владельца**, проверить несоответствия и записать `ARCHITECTURE.md` с моделями, границами хранения, схемой сохранений, событиями боя и планом end-to-end этапов. Показать владельцу для утверждения, как прямо требует исходное ТЗ.
2. Сохранить все системы GDD в целевом охвате. Реализовывать последовательно и доводить каждый вертикальный срез до игры на телефоне: живой бой → Рог и выпадение → сравнение/надеть/распылить → прогрессия → следующие системы.
3. Каждое изменение проверять `typecheck`, `build`, функциональными тестами и визуальными мобильными проверками. Перед признанием функции завершённой — реальный Telegram WebView на телефоне владельца.
4. Не сливать и не публиковать изменения в действующую TERRITORY. Новое приложение должно иметь отдельный тестовый URL и отдельную тестовую Telegram-интеграцию.
5. Статус сообщать честно: реализовано / демонстрация / заблокировано / не проверено на устройстве. Без подмены результата отчётом.

## Технические риски из GDD для ARCHITECTURE.md
- CloudStorage/localStorage — ненадёжный источник истины для валют, рефералов, Stars, боёв и наград. Нужна независимая серверная валидация для сетевых/денежных функций.
- Оплату Stars, рефералов, награды и время офлайн-дохода нельзя доверять клиенту.
- Проверить на практике API Telegram и режимы браузера; не выдумывать ссылку для `openTelegramLink()`.
- Формулы баланса и скорость прогрессии должны быть воспроизводимыми и тестируемыми.
